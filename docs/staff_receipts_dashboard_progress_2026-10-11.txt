1. 제조사 접수 확인·거절
- API: POST /api/v1/manufacturer-orders/{audit_log_id}/reception
- 제조사 앱 대신 직원이 제조사 답변을 확인하고 결과를 기록한다.
- 접수 확인은 ACCEPTED, 거절은 REJECTED로 저장한다.
- 확인 방법은 PHONE / EMAIL / OTHER이며 실제 전화나 이메일을 보내지 않는다.
- 확인 방법·메모·처리 직원·시간을 기존 audit_logs에 저장한다.
- 거절 사유는 필수이며 메모는 최대 2,000자이다.
- 본사 사원은 본인 발주, 팀장·이사·ADMIN은 전체 발주를 기록한다. 임원 단독 직책은 조회 전용이다.
- ORDERED 품의만 처리하고 부모 품의 잠금으로 동시 처리를 직렬화한다.
- 동일 직원·요청 ID·본문의 재시도는 기존 결과를 반환한다. 다른 요청으로 확정된 결과를 덮어쓰면 409이다.

2. 접수 확인 시 본사 전체 자동 입고
- goods_receipts.py에서 저장된 발주 품목과 수량을 사용하여 전량 입고한다.
- 접수 확인 시 물품이 모두 본사에 도착한 것으로 간주하는 프로젝트 규칙이다.
- 접수 거절은 본사 재고를 변경하지 않는다.
- audit_logs에 PROCUREMENT_GOODS_RECEIVED 입고 기록을 추가한다.
- headquarters_inventory의 on_hand_quantity를 증가시킨다.
- reserved_quantity와 defective_quantity는 유지하고 available_quantity는 기존 생성 컬럼으로 계산한다.
- 재고 행이 없으면 기존 headquarters_inventory에 행을 생성한다.
- inventory_movements에 품목별 입고 증가량·처리 후 재고·처리 직원·품의 참조를 기록한다.
- 품의를 먼저 잠그고 제품 옵션 ID 순으로 재고를 잠근다.
- 접수 기록·입고 기록·재고 변경·재고 이동 이력을 하나의 트랜잭션으로 저장한다.
- 실패 시 전체 롤백하고 같은 요청 재시도로 입고량이 중복 증가하지 않도록 한다.
- 기존 입고 기록·이동 이력, 잘못된 수량·품목, 저장 가능한 재고 수량 초과를 차단한다.
- 과거 버전에서 접수 확인만 저장한 건은 자동으로 소급 입고하지 않는다.
- 품의 상태는 ORDERED로 유지한다.

3. 제조사 발주 Flutter UI
- 발주 상세의 버튼을 접수 확인 및 전체 입고로 변경했다.
- 확인 창에 발주 총수량과 본사 재고 자동 반영 안내를 표시한다.
- 전체 입고 확정 시 API 응답의 goods_receipt로 실제 입고 수량을 안내한다.
- 목록·상세에 입고 완료 수량과 입고일을 표시한다.
- 상세에 품목별 입고 수량과 입고 처리 후 본사 실물 재고를 표시한다.
- 처리 후 재고는 입고 당시 이력이며 현재 재고와 구분한다.
- 입력·요청 식별자를 유지한 재시도, 저장 중 버튼 비활성화, 중복 처리 방지를 적용했다.
- 입고 로그가 없는 과거 접수 기록은 입고 기록 없음으로 표시한다.

4. 대리점 대시보드 현재 보관 수량
- API: GET /api/v1/dashboard/branches/{branch_id}/inventory
- branches와 pickup_holdings를 사용해 해당 지점의 전체 보관 수량을 합산한다.
- 포함 상태: INSPECTING / READY_FOR_PICKUP / RECALLING / DAMAGED.
- 제외 상태: AWAITING_ARRIVAL / PICKED_UP / RETURNED_TO_HQ / CANCELED.
- held_quantity는 켤레 수, holding_count는 보관 기록 건수이다. 페이지 제한 없이 집계한다.
- 로그인 직원의 활성 소속 지점만 조회할 수 있다.
- 대리점 사원·점장 대시보드의 현재 보관 수량 카드에 실제 데이터를 표시한다.
- 지점 변경·새로고침 시 재조회한다. 오류 시 이전 수량이나 목업 수량으로 대체하지 않는다.
- 나머지 미연결 대리점 카드는 API 연결 예정으로 표시한다.

5. 본사 대시보드 재고 부족
- API: GET /api/v1/dashboard/headquarters/low-stock
- 본사 사원·팀장·이사·임원·ADMIN만 조회한다.
- headquarters_inventory, product_variants, products, inventory_policies를 사용한다.
- 본사 재고 행이 있는 활성 제품·옵션을 집계한다. 비활성 재고 정책은 제외한다.
- 활성 정책의 초기 수량과 기준 퍼센트를 사용하고 정책이 없으면 100개·30%를 적용한다.
- 가용 수량이 기준 미만인 옵션 수를 집계한다. 기본 기준에서 29개는 부족, 30개는 부족 아님이다.
- 카드에 N종으로 표시하고 실제 부족 옵션 수로 업무 알림을 생성한다.
- 확인 시점 실제 DB 집계: 242개 옵션 중 41개 부족. 이후 입고·예약 등에 따라 값은 달라질 수 있다.

6. 임원 대시보드 판매 지표
- API: GET /api/v1/dashboard/executive/sales
- EXECUTIVE / ADMIN 직책만 조회한다.
- 한국 시간 기준 오늘 포함 28개 날짜의 첫날 00:00부터 조회 시각까지 결제 완료 시간으로 집계한다.
- PAID / PREPARING / SHIPPING / READY_FOR_PICKUP / COMPLETED 주문을 대상으로 한다.
- PAID 또는 PARTIALLY_REFUNDED 결제 기록이 필요하다. 미결제·취소·전액 환불은 제외한다.
- 주문별 결제 기록과 품목 수량을 먼저 그룹화하여 중복 집계를 방지한다.
- 판매량: 주문 품목 수량 합계. 매출: orders.paid_total 합계. 주문 수: 결제 완료 주문 건수.
- 매출은 쿠폰·적립금 사용 이후 결제액이며 부분 환불 차감 전이다. 화면에 집계 기준을 명시한다.
- 실제 로그인 임원 화면의 최근 28일 판매량·매출·주문 카드를 연결했다.
- 판매 조회 실패 시 조회된 재고 부족 지표는 유지하고 판매 지표만 오류로 표시한다.
- 확인 시점 실제 DB 집계: 판매량 50켤레, 결제액 5,697,500원, 주문 44건. 조회 시점과 기간에 따라 달라진다.

7. DB·인증·범위
- 테이블·컬럼 구조는 변경하지 않았다.
- 실제 제조사 전송·배송 단계와 본사에서 대리점으로 보내는 배송 처리까지 구현한 것은 아니다.
- 새 대시보드 API는 Firebase 인증, DB 직책 또는 소속 지점 검사를 사용한다.
- 기존 재고 목록 API의 인증 적용 여부는 변경하지 않았다.
- 실제 화면의 아직 연결하지 않은 지표는 API 연결 예정으로 표시하고 미리보기는 기존 목업을 유지한다.
