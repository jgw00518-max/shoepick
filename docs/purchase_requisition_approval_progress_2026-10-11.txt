1. 오늘 진행한 작업 — 제조사 자동 발주 등록
- 이사 최종 승인 시 기존 audit_logs에 발주 기록을 자동 생성한다.
- 제조사 앱·계정·수주 테이블과 새로운 DB 테이블·컬럼을 추가하지 않는다.
- purchase_approvals.py에서 결재를 APPROVED로 기록하고, manufacturer_orders.py의 발주 등록 함수를 같은 DB 연결로 호출한다.
- 품의 상태는 PENDING_DIRECTOR에서 ORDERED로 변경한다.
- 발주번호는 PO-{품의 ID 6자리} 형식이다.
- audit_logs의 action_code=PROCUREMENT_ORDER_PLACED, entity_type=PURCHASE_REQUISITION, entity_id=품의 ID를 사용한다.
- after_data JSON에 제조사, 제목·사유, 상품 코드·이름·옵션·승인 수량 등의 발주 당시 스냅샷을 저장한다.
- 처리 직원 ID와 등록 시간을 기존 감사 로그 컬럼으로 기록한다.
- 품의를 잠근 뒤 기존 발주 기록을 검사하여 동시 승인·재시도의 중복 발주를 차단한다.
- 발주 기록 저장 실패 시 이사 승인과 품의 상태 변경도 함께 롤백한다.
- 팀장 승인과 이사 반려에서는 자동 발주가 생성되지 않는다.
- 발주 생성으로 본사 재고를 증가시키지 않는다.

2. 오늘 진행한 작업 — 제조사 발주 목록·상세 조회
- 목록 API: GET /api/v1/manufacturer-orders
- 상세 API: GET /api/v1/manufacturer-orders/{audit_log_id}
- 상세 조회에는 발주번호나 품의 ID가 아닌 목록 응답의 audit_log_id를 사용한다.
- page, page_size, order(desc/asc), keyword를 지원한다.
- 제조사 이름·품의 제목·발주번호 검색, 최신순·오래된순 정렬, 페이지 이동을 구현했다.
- 제조사·상품·옵션·수량은 저장된 발주 스냅샷에서 읽는다.
- 현재 품의 상태와 작성자·등록자 이름은 purchase_requisitions, employees에서 읽는다.
- 서버에서 확인한 활성 DB 직책으로 조회 범위를 결정한다.
- HQ_STAFF: 본인이 작성한 품의에서 생성된 발주만 조회한다.
- TEAM_LEAD / DIRECTOR / EXECUTIVE / ADMIN: 전체 발주를 조회한다.
- 대리점 직책만 가진 직원은 조회할 수 없다.
- 여러 직책을 가진 테스트 계정은 기존 본사 직책을 통해 전체를 조회한다. 이메일 예외 처리는 추가하지 않았다.
- 미인증은 401, 접근 권한 부족은 403, 없는 기록 또는 범위 밖 상세는 404로 처리한다.
- 실제 MySQL에서 기존 발주 1건의 목록·검색·상세 조회를 읽기 전용으로 확인했다.

3. 오늘 진행한 작업 — Flutter UI 연결
- 본사 사원·팀장·이사·임원 메뉴에 제조사 발주를 추가했다.
- 대리점 메뉴에는 제조사 발주를 표시하지 않는다.
- 발주 목록에 발주번호·제목·제조사·품목 수·총수량·등록자·등록일을 표시한다.
- 검색, 최신순·오래된순, 페이지 이동, 새로고침, 오류·빈 목록 안내를 연결했다.
- 상세 팝업에 근거 품의·현재 상태·사유·발주 당시 전체 품목을 표시한다.
- 이사 승인 안내에 자동 발주 등록을 명시하고 성공 시 발주번호를 표시한다.
- Firebase 없는 미리보기에서는 실제 발주 조회 대신 로그인 안내를 표시한다.

4. 전달 상태와 현재 구현 범위
- 현재 transmission_status는 NOT_SENT이며 앱 표시 문구는 외부 전송 전이다.
- transmission_status는 신규 컬럼이 아닌 audit_logs.after_data JSON의 항목이다.
- 자동 발주 등록은 내부 업무 기록 생성이다. 제조사에 실제 이메일이나 API를 전송하지 않는다.
- 발주 전달 완료 기록, 제조사 접수·거절 확인, 부분·전체 입고 등록은 아직 구현하지 않았다.
- 입고에 따른 본사 재고 증가와 입고 현황은 후속 작업이다.
- 감사 로그는 발주 원본으로 사용하므로 삭제·보관 기간 정리 대상에서 제외해야 한다.
