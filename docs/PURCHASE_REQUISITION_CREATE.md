# 제조사 구매 품의 작성 API

`POST /api/v1/purchase-requisitions`는 품의와 품목을 한 트랜잭션으로 저장하고 201을 반환한다.
작성 단계는 DRAFT이며 상신은 아래 별도 API에서 처리한다. 작성 시 결재·발주·재고 증가는 수행하지 않는다.

Firebase ID 토큰을 `Authorization: Bearer <token>` 헤더에 전달한다.
활성 직원이며 기존 `PROCUREMENT_REQUISITION_CREATE` 권한이 있어야 한다.
요청 본문으로 작성자 ID·상태·결재 경로를 지정할 수 없다.
작성자는 로그인한 직원이고 결재 경로는 활성 `PROCUREMENT_STANDARD`를 사용한다.
테스트 직원(기존 employee_id=15)은 현재 해당 작성 권한을 보유한다.
이 API 구현으로 직원의 다른 권한이나 DB 스키마는 변경하지 않았다.

```json
{
  "manufacturer_id": 1,
  "branch_id": null,
  "title": "제조사 운동화 구매 품의",
  "reason": "본사 부족 재고 보충",
  "items": [
    {"product_variant_id": 12, "requested_quantity": 100}
  ]
}
```

제조사·상품 옵션 ID는 예시이므로 실제 DB에서 해당 제조사에 속한 활성 옵션을 사용한다.
branch_id는 생략 가능하며 입력하면 직원의 현재 활성 소속 지점이어야 한다.
품의 하나에 한 제조사 상품만 담는다. 제목 1~150자, 사유 1~2000자,
품목 1~100개이며 중복 옵션을 허용하지 않는다. 수량은 양의 정수이다.

응답은 `data` 안에 purchase_requisition_id, requested_by_employee_id, branch_id,
approval_workflow_id, manufacturer_id/name, title, reason, requisition_status,
submitted_at(null), created_at, items를 반환한다.
items에는 생성된 purchase_requisition_item_id, product_variant_id,
requested_quantity와 상품명·코드·색상·사이즈를 포함한다.

제조사 정보는 기존 products.manufacturer_id로 검증한다. 현재 품의 테이블에는
제조사 컬럼이 없으므로 별도로 저장하지 않는다. 제조사와 상품명 응답은 작성 시점의 조회 정보이며
역사 스냅샷 저장은 구현하지 않았다. 향후 발주 때 상품의 제조사를 다시 확인해야 한다.

| HTTP | 의미 |
|---|---|
| 201 | 초안 생성 완료 |
| 400 | 입력 형식·중복 옵션·다른 제조사 품목 |
| 401 | Firebase 인증 필요 |
| 403 | 직원 작성 권한·지점 접근 권한 없음 |
| 404 | 제조사·상품 옵션 없음 |
| 409 | 비활성 상품·옵션 또는 활성 표준 결재 경로 없음 |
| 500 | DB 등 내부 오류(연결 정보·SQL 미노출) |

POST를 다시 보내면 새 초안이 생성된다. 네트워크 실패에 대한 자동 재시도·중복 생성 방지 키는
아직 지원하지 않으므로 앱에서 작성 버튼 연속 클릭과 자동 재전송을 방지해야 한다.
## 직원 앱 연결

일반 Firebase 로그인 → 본사 사원 → 품의 작성 화면에서 실제 API를 사용한다.
`GET /api/v1/purchase-requisitions/creation-options`는 같은 작성 권한을 확인하고
활성 제조사 상품 옵션과 본사 실물 재고량을 반환한다. 제조사 선택에 맞춰 상품 목록을 필터링한다.
현재 화면은 상품 옵션 하나씩 초안을 작성한다. API 자체는 품목 여러 개를 지원한다.
버튼은 `품의 초안 저장`이며 작성 성공 시 품의 번호와 DRAFT 상태를 표시한다.
최근 품의는 DB 목록을 조회한다. 화면 진입·목록 새로고침·저장 완료 시 다시 불러온다.
상신은 최근 품의의 상신 버튼으로 연결했다. 팀장·이사 승인·반려 API는 아직 미연결 상태이다.
목업 바로 보기는 기존 샘플 품의 생성·상신을 사용한다.
저장 중 버튼을 비활성화하고 네트워크 실패를 자동 재시도하지 않는다.
Firebase 토큰은 자동으로 요청에 포함하며 401에 한해서 갱신 후 한 번 재시도한다.
직원 앱에서 토큰을 직접 입력할 필요가 없다.

## 최근 품의 조회

`GET /api/v1/purchase-requisitions?page=1&page_size=20&status=DRAFT`

status는 생략하면 전체 상태를 조회한다. page는 1 이상, page_size는 1~100이다.
작성일 내림차순, 같은 작성일에서는 품의 ID 내림차순으로 반환한다.
응답은 `data` 목록과 `pagination`(page/page_size/total_count)이다.
각 품의에 ID, 제목, 작성자 ID·이름, 지점 ID·이름, 상태, 작성·상신일,
품목 개수와 요청 수량 합계를 포함한다. 품목 여러 개도 품의 한 건으로 센다.

활성 직원의 기존 권한을 사용한다. 작성·상신 권한은 본인 작성 품의만 조회한다.
팀장·이사 결재, 감사 로그 조회, 권한 관리 중 하나의 권한이 있으면 전체 품의를 조회한다.
테스트 계정 staff@example.com의 기존 이사 결재 권한으로 전체 품의를 조회할 수 있다.
요청의 employee_id나 화면에서 선택한 직책은 권한 판단에 사용하지 않는다.
Flutter에서 상태 필터·20건씩 이전/다음 페이지·목록 새로고침을 지원한다.
새 초안 저장 뒤 상태 필터를 해제하고 첫 페이지로 돌아가 DB 목록을 다시 조회한다.
목록 조회 실패는 저장 실패와 별도로 안내하며 다시 조회할 수 있다.

## 초안 수정

- `GET /api/v1/purchase-requisitions/{id}`: 품의와 전체 품목, 변경 확인용 revision을 조회한다.
- `PATCH /api/v1/purchase-requisitions/{id}`: 제목·사유·제조사 상품 품목·수량을 일괄 수정한다.

PATCH 본문은 작성 API 본문과 같은 필드에 상세 조회의 revision을 추가한다.
기존 branch_id를 그대로 보내야 한다. 작성자·소속 지점·결재 경로·상태·작성일은 변경하지 않는다.
작성 권한이 있는 본인 작성 DRAFT 품의만 수정 가능하다. 결재 권한으로 타인 품의를 조회해도
타인의 초안을 수정할 수는 없다. 목록의 can_edit가 현재 수정 가능 여부를 반환한다.
행 잠금으로 상태 변경과 수정을 직렬화하고, 다른 곳에서 먼저 수정했으면 revision 불일치로 409를 반환한다.
품의와 품목 교체는 단일 트랜잭션이다. 실패 시 원래 제목·품목을 모두 복원한다.

직원 앱: 최근 품의 → 수정 → 제목·사유·제조사·품목·수량 변경 → 수정 저장.
기존 전체 품목을 불러오며 품목 추가·삭제도 가능하다. 제조사 변경 시 각 품목의 상품을 다시 선택한다.
수정 창은 스크롤되며 저장 중 중복 요청·닫기를 막는다. 실패 시 입력을 유지하고 다시 불러올 수 있다.
저장 또는 취소로 창을 닫으면 목록을 재조회한다. 목업 품의에는 실제 DB 수정 버튼을 추가하지 않았다.

## 초안 상신

`POST /api/v1/purchase-requisitions/{id}/submit`

본문은 상세 조회에서 받은 `{"revision":"64자리 변경 확인 문자열"}`이다.
기존 `PROCUREMENT_REQUISITION_SUBMIT` 권한이 있는 활성 작성자 본인만 상신할 수 있다.
현재 내용·상태를 행 잠금으로 확인하며 DRAFT만 상신한다. 내용이 변경됐으면 409로 거절한다.
빈 품목·다른 제조사 품목·비활성 옵션·잘못된 수량·빈 제목·사유와 지점 접근 범위를 다시 검증한다.
품의의 기존 결재 경로가 활성이고 팀장 1단계·이사 2단계 역할이 활성인지 확인한다.
두 단계의 purchase_approvals 기록을 PENDING으로 만들고,
품의를 PENDING_TEAM_LEAD로 변경하면서 submitted_at에 DB 현재 시각을 기록한다.
두 작업은 같은 트랜잭션이다. 오류 시 결재 기록·상태·시간을 모두 롤백한다.
이미 상신된 품의나 결재 기록이 있는 초안은 409로 거절하며 결재 기록을 중복 생성하지 않는다.
이사 기록도 대기 상태로 준비하지만 실제 이사 결재는 팀장 승인 이후에만 허용해야 한다.
향후 purchase_approvals.py에서 품의 상태·결재 순서 검사를 함께 구현해야 한다.

직원 앱에서 최근 품의 → 상신 → 상세 내용 확인 → 상신 확인 순서로 사용한다.
목록의 can_submit이 현재 상신 가능 여부이다. 상신 중 다른 작업·중복 클릭을 차단하고
성공하면 최신 목록과 팀장 결재 대기 상태를 표시한다. 상신된 품의는 수정·상신 버튼이 사라진다.
목업의 기존 작성·상신 시뮬레이션은 그대로 유지한다.
